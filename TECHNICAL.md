# Technical Reference — Kebabfuscator v1 Deobfuscator

This document explains the internals of Kebabfuscator v1's protection scheme and how each analysis pass reverses it. It is companion reading to the source code; the main README covers usage.

---

## Kebabfuscator v1 Protection Overview

A protected script has four protection layers applied in sequence during obfuscation:

1. **Identifier randomization** — every internal variable name is replaced with a fresh random identifier on each run.
2. **String encryption** — all string literals are encrypted with a per-script stream cipher and stored as encoded blobs. At runtime, the script decodes them before use.
3. **VM compilation** — the entry chunk is compiled to a custom bytecode format and embedded inline. A bespoke VM interpreter executes it.
4. **Anti-tamper** — the lifted entry chunk contains environment checks (Lune, Luau sandbox, Roblox DataModel structure) that crash the script when the checks fail.

The deobfuscator reverses layers 1–3 entirely statically. Layer 4 is preserved and optionally extracted (`--antitamper`).

---

## Stage 1 — Identifier Canonicalization (`names.py`)

### The problem

Every run of Kebabfuscator regenerates names for ~60 internal symbols. The seed family (`jm1..jm32` + `jmf/jms/jmt/jmu/jmw`), crypto functions (`oE55`, `CA56`, `Nx58`, `rc57`, `j915`, `JN10`, `NS14`, `pW17`, `Ww18`, `bc19`, `Ox20`), loader variables, and VM internals all change names. Because the downstream passes reference these by name, the first step is to stably identify each one and rewrite the source to the canonical spelling.

### How recognition works

Canonicalization relies on **structural anchors** — text patterns in the source that are identical across all runs regardless of identifier names. Examples:

- The seed family is identified by finding 32 sequentially numbered `local` declarations with the same prefix appearing in order at the top of the file.
- The base-85 decoder (`oE55`) is recognized by its unique loop pattern: `local function <name>(s) local o={} for i=(`.
- The stream cipher (`Nx58`) is recognized by its XOR accumulator pattern referencing the already-identified `Ww18` and `bc19` functions.
- The VM dispatcher (`c435`) is recognized by its characteristic parameter signature referencing the already-identified loader variables.

Each anchor is matched with a targeted regex after the symbols it depends on are already resolved, so the resolution order matters and is encoded in `resolve()`.

### Output

A rewritten source string with all ~60 randomized identifiers replaced by canonical names. Encrypted string payloads are never touched — rewriting bytes inside a cipher blob would corrupt the data.

## Stage 2 — Constants Extraction (`keb.py`)

### What is extracted

After canonicalization, the source contains stable names. `keb.py` scans for specific `local NAME = <expr>` patterns to extract:

| Constant | Role |
|---|---|
| `NS14` | VM dispatch key — determines the opcode→handler mapping for this script |
| `Pq28` | Loader RNG seed — initializes the string-table cipher |
| `Mz25` / digit tables | Base-85 alphabet used by `oE55` |
| `pN65` | String-table blob array (the encrypted payloads) |
| `Z654` | Closure table (the VM program) |

### Expression evaluation

Kebabfuscator obscures numeric constants with arithmetic. For example, the number 102 may appear as `(1*86 + 14*2 - 0)` or `(0*574 + 137)`. `keb.py` includes a small Lua expression evaluator (`newdeob.py` → `LuaExpressionEvaluator`) that handles integer arithmetic, `bit32` operations, `string.byte`, `#string.rep`, and `#"..."` length expressions — the full set that Kebabfuscator uses to encode constants.

## Stage 3 — String Table Decoding (`keb.py`)

### The cipher stack

Kebabfuscator's string encryption uses three layers:

1. **Base-85 (`oE55`)**: Each blob is stored as a base-85-encoded byte string. `oE55` decodes it to raw bytes. The alphabet is derived from the `Mz25` digit tables extracted in Stage 2.

2. **Index fold (`CA56`)**: The decoded bytes are permuted by a fold function that maps every byte through a computed index table, scrambling the byte order.

3. **XOR stream cipher (`Nx58`)**: The folded bytes are XOR'd with a keystream generated by a chained RNG seeded from `Pq28` (the loader seed) and `j915` (a self-modifying key). The RNG state evolves with each byte, so the keystream is different for every position.

All three are reimplemented in pure Python in `keb.py` using 32-bit integer arithmetic (wrapping via `& 0xFFFFFFFF`) to match Lua's `bit32` semantics exactly.

### Output

A list of plaintext string tables. Each blob decodes to a sequence of null-terminated Lua strings. The deobfuscator replaces each `pN65[i]` decode loop in the source with a plain Lua table constructor: `local pN65 = {"string1", "string2", ...}`.

## Stage 4 — VM Bytecode Decoding (`vm.py`, `newdeob.py`)

### The VM structure

The Kebabfuscator VM is a register-based interpreter. The entry chunk is stored as a serialized instruction stream in `Z654`. Each instruction encodes:

- **Opcode** — an integer that is XOR'd with the dispatch key `NS14` to get the actual handler index.
- **Operands** — register indices, constant-table indices, or immediate values, packed as integers.

The dispatcher (`c435`) is a large `if/elseif` chain over the decoded opcode. `vm.py` maps each handler to the standard Luau VM opcode it corresponds to (LOADK, MOVE, ADD, CALL, RETURN, CLOSURE, etc.) by matching the handler's body against known patterns.

### Opcode mapping

Because the dispatch key `NS14` varies per script, the same handler is reached by different opcode values in different outputs. The decoder extracts `NS14` dynamically and applies it to invert the mapping, so no hardcoded per-script opcode table is needed. `opcode_map.txt` documents the canonical handler→Luau-opcode correspondence and is used for diagnostics; normal operation derives it from the source.

## Stage 5 — Luau Lifting (`lift.py`)

### From bytecode to source

`lift.py` takes the decoded instruction sequence and reconstructs Luau source. The main challenges:

**Register assignment**: VM registers map to Lua locals. The lifter tracks the type and lifetime of each register across the instruction window to assign meaningful variable declarations and avoid redundant temporaries.

**Control flow**: Conditional jumps (`JUMPIF`, `JUMPIFNOT`, `JUMP`) are reconstructed into `if/elseif/else` and loop structures (`while`, `repeat`, `for`, `for-in`). The lifter uses a simple dominator analysis over the basic block graph to distinguish loop back-edges from forward branches.

**Closures and upvalues**: `CLOSURE` instructions reference proto entries in `Z654`. The lifter recurses into each nested proto, lifting it as a nested `function` definition and wiring upvalue captures (`GETUPVAL`/`SETUPVAL`) to the enclosing scope.

**Constant folding**: Numeric and string constants are looked up from the decoded constant table. String references become the plaintext strings recovered in Stage 3.

### Output dialect

Lifted output targets **Luau**, not Lua 5.1. The output may contain:
- `//` integer division (Luau extension)
- Roblox global APIs (`game`, `workspace`, `Players`, etc.)
- `typeof` type checks

Use a Luau runtime in a Roblox context. The bundled `harness2.lua` translates the two floor-division expressions in the sample to `math.floor(...)` for Lua 5.1 compatibility — it is a sample-specific smoke test, not a general compatibility layer.

## Anti-Tamper Extraction (`--antitamper`)

The lifted entry chunk of the sample begins with an anti-tamper closure (`local b = function()`). It performs environment checks:

- Lune/Lute runtime detection (`_G.lune`, `_G.lute`)
- `@lune/fs` module probe via `pcall(require(...))`
- Roblox `game` and `workspace` userdata type checks
- `typeof` availability and `game.ClassName == "DataModel"` checks
- `workspace.Parent == game` hierarchy check
- Physics probe via `workspace:FindFirstChild` and `BasePart` creation

The `--antitamper` mode detects this closure by its `local b = function(` anchor in the lifted output, extracts it, and emits a Lua module that returns it. The checks inside are preserved exactly — this is for analysis and authorized reuse, not bypassing protection.
